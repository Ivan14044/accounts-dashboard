# Переезд панели на домен accdash.com

Внутренняя дока: пошаговый переезд с `panel.account-factory.site` на
`panel.accdash.com`. Файл лежит в `docs/` — каталог исключён из деплоя
(`exclude` в `deploy.yml`) и закрыт правилом `.htaccess`, наружу не уезжает.

## Зачем

Продление `account-factory.site` у Hosting Ukraine стоит ~3000 грн/год (~$67).
Это цена регистратора за `.site`, а не мировая цена. `.com` у регистратора,
работающего по себестоимости реестра, стоит ~$10,4/год (~470 грн по курсу НБУ
44,71 на 2026-08-17) — примерно в шесть раз дешевле.

Домен `account-factory.site` истёк 2026-08-16 и находится в статусе
`clientHold`. Переезд ограничен по времени, а не «когда-нибудь».

## Что установлено проверкой (2026-08-17)

Эти факты определяют порядок шагов ниже — не меняй порядок, не перепроверив их.

1. **Приложение домен-агностично.** Имя домена нигде в коде не зашито:
   редиректы строятся из `$_SERVER['HTTP_HOST']` (`config.php`, `auth.php`),
   cookie сессии ставятся без параметра `domain` (`includes/SessionManager.php`),
   CSP везде `'self'`, строка подключения к БД вводится при логине и живёт в
   сессии. Значит смена домена **не требует правок в логике** — только в доках
   и в комментариях.

2. **Origin не доверяет заголовкам прокси.** Проверено запросом напрямую к
   `185.104.45.9` с `X-Forwarded-Proto: https` и `CF-Visitor: {"scheme":"https"}`
   и без них — результат одинаковый: `Location: http://…` и cookie без флага
   `secure`. То есть `$_SERVER['HTTPS']` на этом хостинге выставляется только
   реальным TLS-соединением до origin.

   **Следствие, ради которого этот пункт здесь: режим Cloudflare SSL «Flexible»
   для панели непригоден.** В нём Cloudflare ходит к origin по HTTP, origin
   считает соединение незашифрованным, редирект `index.php → login.php` уезжает
   на `http://`, а cookie сессии теряет `secure`. Нужен как минимум **Full**.

3. **У origin нет своего сертификата.** На любое имя домена
   (`panel.`, `www.`, apex, `dashboard.`) хостинг отдаёт заглушку
   `CN=default-ssl.default-host.net`. Поэтому `Full (strict)` включать можно
   только после шага 6 — иначе Cloudflare ответит 526 и панель ляжет.

4. **Служебные каталоги на проде закрыты.** `tools/`, `includes/`, `sql/`,
   `tests/`, `*.md` → 403; `deployed-version.txt` → 200. Проверено запросами.
   Это важно для шага 7: проверять живость прода надо по
   `deployed-version.txt` и `login.php`, а не по файлам из `tools/`.

## Шаг 1. Купить домен

`accdash.com` на 2026-08-17 свободен: whois Verisign отдаёт `No match`, домен
не резолвится (нет A/NS/MX), следов в Wayback нет, бренда с таким именем поиск
не находит. Прошлой жизни у имени нет — репутационных хвостов не будет.

Покупать у регистратора, работающего по себестоимости (Cloudflare Registrar):
там нет промо-цены первого года, поэтому цена регистрации равна цене продления.
Домен сразу заводится в аккаунт регистратора со своими неймсерверами, и
Universal SSL выпускается автоматически — возиться с Let's Encrypt на хостинге
не придётся.

С 1 ноября 2026 оптовая цена `.com` у Verisign растёт с $10,26 до $10,97.
Если регистратор даёт брать сразу на несколько лет — есть смысл взять с запасом.

## Шаг 2. Привязать домен к хостингу

Панель физически лежит на ukraine.com.ua: `/home/if592995/panel.account-factory.site/www/`,
origin `185.104.45.9`. **Файлы и БД никуда не переезжают** — меняется только имя.

Сделано так (проверено на практике 2026-08-17): `panel.accdash.com` добавлен
**псевдонимом** к существующему сайту `panel.account-factory.site`
(в adm.tools: Мои сайты → сайт → Настройки сайта → поле «Псевдонимы»).
Каталог и FTP-пользователь не меняются, поэтому `deploy.yml` трогать не нужно
вообще: он ходит по секрету `FTP_SERVER` с `server_dir: ./`, и FTP-логин
приземляется в тот же каталог.

Три грабли, на которые я наступил — не повторяй:

1. **Корневой каталог чужого сайта указать нельзя.** В настройках сайта поле
   «Корневой каталог» выглядит редактируемым, но его префикс
   `/home/if592995/<домен>/www/` — серый и жёстко зафиксирован; вводится только
   подкаталог внутри него. То есть «создать сайт `panel.accdash.com` и нацелить
   его на каталог старого» — невозможно.

2. **Псевдоним не примут, пока существует одноимённый сайт.** Если сначала
   создать сайт `panel.accdash.com`, попытка добавить такой же псевдоним даёт
   «Использование псевдонима panel.accdash.com невозможно, сайт с таким именем
   уже существует». Порядок обязателен: сначала удалить сайт (Мои сайты →
   удалить поддомен, затем появившаяся ссылка «удалить сайт»; файлы при этом
   не трогаются), и только потом добавлять псевдоним.

3. **Изменения применяются не мгновенно.** adm.tools пишет «в течение 5 минут»,
   по факту конфиг перегенерировался за ~2 минуты. До этого домен отдаёт
   заглушку хостинга, которая редиректит `https://…` → `http://…` на тот же
   URL. Не пугайся и не начинай чинить SSL-режим — просто подожди и перепроверь.

Альтернатива (не выбрана) — завести отдельный сайт `panel.accdash.com` с
каталогом `/home/if592995/panel.accdash.com/www/`. Тогда деплой сломается,
пока не перенастроишь домашний каталог FTP-пользователя или не пропишешь явный
`server_dir`; плюс первый деплой зальёт всё с нуля, так как
`.ftp-deploy-sync-state-panel.json` в новом каталоге отсутствует. Смысл только
в чистом имени каталога.

## Шаг 3. DNS

В панели регистратора (зона `accdash.com`):

```
panel   A   185.104.45.9   proxied (оранжевое облако)
```

Проксирование включить сразу: оно даёт валидный сертификат на edge, не дожидаясь
сертификата на origin. Без него браузер упрётся в заглушку из пункта 3 выше.

## Шаг 4. SSL-режим — Full, не Flexible

В настройках SSL/TLS зоны выставить **Full**.

Обоснование — пункт 2 раздела «Что установлено проверкой». Flexible молча
сломает редиректы и снимет `secure` с cookie сессии; `Full (strict)` на этом
шаге даст 526, потому что у origin ещё заглушка вместо сертификата.

## Шаг 5. Проверить, что панель поднялась

```bash
curl -sS -o /dev/null -D - https://panel.accdash.com/index.php | grep -iE '^HTTP/|^location:|^set-cookie:'
```

Приёмка:

- статус `302`, а не `526` и не `525`;
- `Location: https://panel.accdash.com/login.php` — **именно `https`**. Если
  там `http://`, значит режим стоит Flexible: вернись на шаг 4;
- в `Set-Cookie` есть флаг `secure`;
- `https://panel.accdash.com/deployed-version.txt` отдаёт 200 и текущий SHA;
- `https://panel.accdash.com/tools/migrations/check_login_index.php` отдаёт 403
  (служебные каталоги закрыты);
- логин проходит, таблица аккаунтов рисуется, консоль браузера чистая.

Известный шум в консоли после включения проксирования:

```
Loading the script 'https://static.cloudflareinsights.com/beacon.min.js/…'
violates the following Content Security Policy directive: "script-src 'self' …"
```

Это Cloudflare Web Analytics: новые зоны автоматически попадают в
аккаунт-уровневый список (Analytics → Web analytics) с пометкой
«Automatic setup», и edge подмешивает beacon в HTML. Наша CSP его блокирует,
поэтому **данные наружу не уходят** — вредa нет, остаётся только строчка в
консоли. Убрать можно двумя способами: отключить сайт в Analytics → Web
analytics (для приватной панели статистика посещений всё равно бесполезна)
либо добавить `https://static.cloudflareinsights.com` в `script-src`
(`includes/ResponseHeaders.php` и `.htaccess`). Первое предпочтительнее:
не расширяет CSP ради внешнего трекера.

Ловушка при проверке: beacon подмешивается только в ответы на запросы, похожие
на настоящий браузер. `curl -A "Mozilla/5.0"` его не увидит — нужны ещё
`Accept: text/html,…` и заголовки `Sec-Fetch-*`. Если ищешь beacon в HTML и не
находишь — это не значит, что его нет.

## Шаг 6. Закрыть origin своим сертификатом

Выпустить Origin Certificate у Cloudflare (живёт 15 лет) и поставить его на
хостинге для `panel.accdash.com`. После этого перевести SSL-режим в
**Full (strict)** и перепроверить по чеклисту шага 5.

Без этого шага участок Cloudflare → origin шифруется, но сертификат на нём не
проверяется, то есть MITM между Cloudflare и хостингом технически возможен.

## Шаг 7. Правки в репозитории

Мержить **только после того, как `panel.accdash.com` реально отвечает** —
иначе доки будут описывать несуществующий домен, а мёрдж в `main` сразу уедет
в прод.

- `.github/workflows/deploy.yml` — `matrix.target.host` (используется в
  подсказке про `deployed-version.txt`) и комментарий про каталог FTP.
  Ветку с правкой `.github/workflows/*` **пушить по SSH**: у HTTPS-remote
  токен без scope `workflow`, push отлетает.
- `DEPLOY.md` — путь на сервере.
- `tools/migrations/README.md` — URL примеров.
- `CLAUDE.md` — раздел «Проверенные факты».

После мёрджа дождаться workflow **Deploy to FTP** до `success` и убедиться, что
`deployed-version.txt` на новом домене показывает свежий SHA.

## Шаг 8. Старый домен

`account-factory.site` отпускается. Учесть:

- регистратор уже сбросил делегирование со своих Cloudflare-неймсерверов на
  собственные (`ns14/ns24/ns34.inhostedns.*`), поэтому старая зона в Cloudflare
  бесполезна — вернуть делегирование на домене в `clientHold` регистратор
  скорее всего не даст;
- на `.site` сейчас **битый HTTPS** (заглушка вместо сертификата), так что до
  переезда ходить на панель безопаснее по новому домену, а не по старому;
- реестр `.site` авто-продлил домен до 2027-08-16, у регистратора есть окно
  выкупа по обычной цене (обычно ~45 дней), дальше — redemption по цене в разы
  выше. Если передумаешь — решать надо в этом окне.

## Откат

Пока старый домен ещё резолвится, откат бесплатный: панель доступна по обоим
именам одновременно (вариант А это позволяет — алиасы не конфликтуют).
Если на новом домене что-то не так — просто продолжай пользоваться старым и
чини новый без спешки. Точка невозврата — снятие делегирования со старого
домена, а не покупка нового.
