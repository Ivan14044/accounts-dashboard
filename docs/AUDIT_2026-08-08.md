## 2. Находки

### Высокий приоритет

**В-1. Ошибка ввода отдаётся как HTTP 500 + HTML вместо 400 + JSON**

Воспроизведено на стенде:

| Запрос к `status_update.php` | Ответ |
|---|---|
| form-encoded вместо JSON | `500`, HTML-страница «Произошла ошибка» |
| JSON без `csrf` | `500`, HTML-страница |
| то же + заголовок `X-Requested-With: XMLHttpRequest` | `400 {"success":false,"error":"CSRF token is required"}` |

Семантика ответа зависит от заголовка, который клиент может не прислать:
`ErrorHandler::isApiRequest()` ([includes/ErrorHandler.php:52](../includes/ErrorHandler.php)) считает
запрос API-шным только по `X-Requested-With`. Для эндпоинта, который умеет
отвечать только JSON, это неверно: ошибка клиента маскируется под отказ сервера,
мониторинг видит всплеск 500, а в ответе прилетает HTML вместо JSON.

Там же в логе — бессмысленный текст `Invalid JSON format: No error`
(`json_last_error_msg()` вызывается, когда декодирования не было).

**Что сделать:** признавать запрос API-шным по `Content-Type: application/json`
или по самому факту, что файл — эндпоинт; `InvalidArgumentException` → 400,
и только неожиданные исключения → 500. Починить текст сообщения.

**В-2. Вес страницы: ~9 000 DOM-узлов на 50 строк**

Замерено на стенде (300 записей, 46 колонок данных):

| Что | Значение |
|---|---|
| HTML `index.php` (50 строк) | 978 554 байт сырых / **40 450 байт gzip** |
| Из них `<tbody>` | 810 KB |
| `data-*` атрибуты | 256 KB |
| DOM-узлов | **8 978** |
| Ячеек `<td>` | 2 500 |
| При `per_page=200` | 3 474 744 байт сырых |
| Отдельных JS-файлов | 31 |
| Отдельных CSS-файлов | 11 |

По сети это дёшево (Brotli на проде), но **парсинг и память в браузере — нет**:
на 200 записей DOM разрастается примерно до 35 тысяч узлов. Это и есть корень
жалоб на «тормозит таблица», а не запросы к БД: сами страницы отдаются за
4–70 мс.

**Что сделать (по возрастанию цены):** не рендерить `data-*` для колонок, которые
не участвуют в JS-логике; включить существующий `table-module.js` (виртуализация)
на больших `per_page`; собрать 31 JS и 11 CSS в бандлы — `build_assets.php` в
проекте уже есть, но страницами не используется.

**В-3. Мобильная вёрстка: футер таблицы обрезается**

При вьюпорте 375×812 (замер в браузере): у `body` горизонтального скролла нет
(правильно), таблица скроллится внутри контейнера (правильно), но элементы
футера — `.dashboard-table__footer-info`, `.dashboard-table__per-page`,
`.dashboard-table__pagination` — уходят вправо до **405px при ширине 375px** и
обрезаются, потому что `body { overflow-x: hidden }`
([assets/css/core-mobile.css:30](../assets/css/core-mobile.css)) прячет вылет вместо того, чтобы его чинить.

То есть на телефоне часть пагинации и селектор «записей на странице» физически
недоступны. `overflow-x: hidden` на `body` — вообще плохой инструмент: он делает
`body` скролл-контейнером (вычисленный `overflow-y` становится `auto`) и маскирует
любые будущие вылеты вёрстки.

**Что сделать:** футер на узких экранах — в колонку/с переносом, а `overflow-x:
hidden` у `body` убрать после того, как вылет исправлен по существу.

**В-4. Выгрузка истории изменений в CSV портит значения с обратными слэшами**

Проект знает про грабли `fgetcsv/fputcsv` с дефолтным `escape='\'` и лечит их
через `escape=''`: так сделано в [export.php:42](../export.php), в
[includes/CsvParser.php:37](../includes/CsvParser.php) и в
[download_account_template.php:49](../download_account_template.php). Но в
[admin_logs.php:124,127](../admin_logs.php) экспорт истории изменений вызывает
`fputcsv()` **с дефолтным escape**.

Проверено запуском на `php:8.2-cli` (round-trip одного и того же значения
`[{"name":"c","value":"{\"id\":\"abc\"}"}]`):

| Как пишем | Строка в CSV | Читается обратно без потерь |
|---|---|---|
| `fputcsv(...)` дефолт — как в `admin_logs.php` | `x,"[{""name"":""c"",""value"":""{\"id\":\"abc\"}""}]"` | **НЕТ** |
| `fputcsv(..., '"', '')` — как в `export.php` | `x,"[{""name"":""c"",""value"":""{\""id\"":\""abc\""}""}]"` | ДА |

В историю изменений попадают старые/новые значения полей — в том числе `cookies`
и `token`, где обратные слэши обычное дело. То есть выгруженная история такого
изменения будет искажена ровно тем багом, который в основном экспорте уже
починили. Данные в БД целы, портится артефакт выгрузки.

**Что сделать:** привести `admin_logs.php` к общей обёртке (`export.php:36-42`
уже её содержит — вынести в `Utils`/`CsvParser` и использовать везде), покрыть
тестом round-trip.

### Средний приоритет

**С-1. Одна фича реализована дважды, и обе живут одновременно**

`custom cards` грузятся и в [dashboard-init.js:2485](../assets/js/dashboard-init.js), и в
[features/custom-cards.js:59](../assets/js/features/custom-cards.js). Результат виден в сетевой панели:
на одну загрузку дашборда уходит **три** одинаковых запроса
`GET /api/settings?type=custom_cards`.

Там же по мелочи: `escapeHtml()` определён трижды (`trash.js:557`,
`filters-modern.js:7`, `modules/utils.js:58`), хелпер `getElementById()` — в пяти
файлах. Это ровно та болезнь, о которой предупреждает шапка `dashboard-stats.js`.

**С-2. Глобальные функции переопределяются по цепочке**

`window.refreshDashboardData` объявляется в
[dashboard-refresh.js:337](../assets/js/modules/dashboard-refresh.js), а затем **оборачивается** ещё дважды:
[favorites.js:472](../assets/js/favorites.js) и [modules/undo.js:151](../assets/js/modules/undo.js). Поведение зависит
от порядка подключения скриптов; обёртка в `favorites.js` вдобавок глотает
`AbortError` всей цепочки. Отладка такого — боль.

**Что сделать:** подписка вместо патча — `DashboardRefresh.onAfterRefresh(cb)`.

**С-3. `tests/test_csv_cookies.php` — не тест**

Файл печатает `✗ FAIL — DATA CORRUPTED` и **всегда завершается кодом 0**. Имя
подходит под маску CI-гейта `tests/test_*.php`, то есть в CI он создаёт иллюзию
покрытия импорта CSV, ничего не проверяя. По сути это диагностический скрипт про
`escape=''` в `fgetcsv`.

**Что сделать:** превратить в настоящий тест с assert-ами (тема важная — порча
cookies при импорте) либо переименовать в `tests/diagnose_csv_cookies.php`.

**С-4. Схема-менеджер пишет ERROR при каждом заходе**

`DatabaseSchemaManager` пытается создать индекс `idx_id_soc_account` по колонке,
которой нет в эталонной схеме → `[ERROR] Failed to create index` на каждый запрос
к дашборду. На работу не влияет, но зашумляет лог и маскирует настоящие ошибки.
Вынесено в отдельную задачу.

**С-5. Документация расходится с кодом**

- `PROJECT_AUDIT.md` держит в разделе «CRITICAL — немедленное исправление» восемь
  пунктов, из которых проверенные мной **уже закрыты**. Доку, которая пугает
  несуществующими дырами, читать перестают.
- `DEVELOPER_GUIDE.md` описывает порядок подключения из шести групп скриптов;
  фактически страница грузит 31 JS-файл, и `density-toggle.js`, `per-page.js`,
  `theme-toggle.js`, `cards-hide-sync.js`, `cell-actions.js`, `undo.js`,
  `dashboard-export.js` в руководстве не упомянуты вообще.

**С-6. На прод уезжает неиспользуемый код**

`deploy.php` (FTP-заливка проекта, требует переменных окружения, которых нет) и
`build_assets.php` (сборщик, страницами не используется) попадают на прод — их нет
в `exclude` списка деплоя. Обе точки закрыты авторизацией (проверено: 302 на
логин), но держать на проде рабочий FTP-загрузчик, которым никто не пользуется, —
лишний риск без выгоды.

**С-7. 55 подавлений ошибок через `@`**

Часть оправдана (запись лога не должна ронять приложение), часть прячет реальные
сбои. Пройтись и оставить `@` только там, где сбой действительно не важен, добавив
комментарий «почему».
