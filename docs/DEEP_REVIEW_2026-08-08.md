# Глубокий разбор — что отделяет проект от «сделано сильной командой»

Второй заход после [аудита](AUDIT_2026-08-08.md). Первый смотрел вширь
(безопасность, корректность, вёрстка) на 300 строках. Этот — вглубь и **под
настоящим объёмом**: в базу залито 180 300 аккаунтов с реальными по размеру
`cookies` и `token`.

Главный вывод: код проекта не плохой. Плохо то, что **он никогда не проверялся
под нагрузкой, на которой работает**. На 300 строках дашборд открывается за
44 мс, на 180 тысячах — за 1,4–2,0 секунды, и почти всё это время тратится не
там, где кажется.

> **Статус (обновлено 2026-08-09).** Семь из восьми пунктов плана закрыты —
> см. таблицу в разделе 4. Кратко: индекс `(deleted_at, status)` ускорил самый
> дорогой запрос с 497 до 18 мс, кэш агрегатов с инвалидацией по данным дал
> 0,22 → 0,04 с на странице, запросов к БД на загрузку стало 19 вместо 49,
> `dashboard-init.js` ужался с 4033 до 2472 строк, в CI появился MySQL и
> интеграционные тесты, в логах — `req=<id>` и тайминг. Один пункт (график за
> 7 дней) оказался **ошибкой замера** и снят. Числа в разделе 1 — это состояние
> ДО работ; они оставлены как точка отсчёта.

## 1. Профиль страницы под реальным объёмом

Замер на стенде: 180 300 строк, `php:7.4-cli`, MySQL 8.0, страница `index.php`
(50 строк на страницу).

| Что происходит на каждый показ страницы | Время |
|---|---:|
| сводный `SUM(CASE ...)` по всей таблице (счётчики шапки) | **412 мс** |
| ~~`GROUP BY DATE(created_at)` — график за 7 дней~~ | ~~250–516 мс~~ → **4,9 мс** (замер был неверный, см. ниже) |
| `GROUP BY status` — карточки статусов | **497 мс** |
| `GROUP BY status` — уникальные значения для фильтров | **290 мс** |
| 13 × проверка существования индекса в `INFORMATION_SCHEMA` | ~74 мс |
| 19 × `SELECT DATABASE()` | мусор, но показателен |
| **Всего запросов к БД на одну загрузку** | **49** |

Для сравнения: `refresh.php` (то же самое, но только таблица, без агрегатов) —
**0,57 с**. То есть **три четверти времени страницы — это агрегаты**, которые
не меняются при переходе со страницы 1 на страницу 2 того же фильтра, но
считаются заново каждый раз.

### Что с этим делать, по убыванию отношения «выигрыш / риск»

**1. Индекс `(deleted_at, status)` — проверено, работает**

Сейчас оптимизатор берёт `idx_deleted_at` и делает `Using temporary`.
Существующий составной индекс `idx_status_deleted` — это `(status, deleted_at)`,
то есть порядок колонок обратный тому, что нужно этим запросам.

```
до:    key: idx_deleted_at      Extra: Using index condition; Using temporary   497 мс
после: key: idx_deleted_status  Extra: Using where; Using index                  18 мс
```

Один индекс чинит сразу два запроса: карточки статусов 497 → **18 мс**,
уникальные значения фильтров 290 → **56 мс**. Это ~27-кратное ускорение самого
дорогого запроса страницы.

Добавление индекса — изменение схемы боевой БД, поэтому **сделано не будет без
отдельного согласия**. На 180k строк MySQL 8 строит такой индекс онлайн (INPLACE,
без блокировки записи), но операция не мгновенная и её стоит делать осознанно.

**2. Не считать агрегаты при пагинации и сортировке**

Переход на страницу 2 меняет только `LIMIT/OFFSET`. Счётчики, карточки статусов,
список значений фильтров и график при этом идентичны. Сейчас они пересчитываются
все четыре раза. Это чистая архитектурная правка без изменения схемы: считать
агрегаты один раз на набор фильтров и переиспользовать при смене страницы —
ровно так, как это уже делает AJAX-путь `refresh.php`.

**3. Короткий кэш агрегатов (30–60 секунд)**

Числа в карточках — не банковский баланс. Даже минутной свежести достаточно, а
экономит это полный скан таблицы на каждый показ страницы у каждого пользователя.

**4. Дешёвая уборка: 19 × `SELECT DATABASE()` и 13 проверок индексов на запрос**

`DatabaseSchemaManager` валидирует схему и существование каждого индекса при
**каждом** заходе. Это правильная идея (самолечащаяся схема), реализованная в
неправильном месте: проверка нужна один раз после деплоя, а не 13 раз в секунду.
Имя базы вообще достаточно спросить один раз на соединение.

**5. График «за 7 дней» — ОШИБКА ЗАМЕРА, чинить нечего**

*Исправлено 2026-08-09.* Здесь стояло, что `GROUP BY DATE(created_at)` не может
использовать индекс и стоит 250–516 мс. Это неверно: я замерил **свой** запрос
без фильтра по дате, а не тот, который выполняет приложение.

Настоящий запрос из `StatisticsService::computeDailyTotals()` содержит
`WHERE created_at >= DATE_SUB(CURDATE(), INTERVAL ? DAY)`. Фильтр по индексу
работает, скан ограничен неделей:

```
type: range   key: idx_created_at   rows: 3150   Extra: Using index condition; Using where; Using temporary
```

Замер на тех же 180 000 строк (данные распределены по 400 дням): **4,9 мс**.
Временная таблица для группировки остаётся, но она строится по трём тысячам
строк, а не по всей таблице.

Вывод: ни функциональный индекс, ни фоновый пересчёт не нужны. Оставлено как
напоминание, что замер надо делать по коду приложения, а не по запросу,
переписанному по памяти.

## 2. Что мешает поддерживать код

Это не «некрасиво», а вещи, которые стоят реального времени на каждой задаче.

### 2.1. Одну таблицу рендерят два места — *частично закрыто 2026-08-09*

Было три реализации: `templates/partials/table/rows.php`,
`assets/js/table-module.js` и класс `Dashboard` в `assets/js/dashboard.js`.
Каждая правка разметки требовала синхронного изменения в трёх местах — и
`colspan` пустой выдачи, и удаление дублирующих `data-*`.

**Здесь была ошибка:** выше стояло, что «сервер уже умеет отдавать готовый HTML —
`refresh.php` возвращает отрендеренный партиал». Это неверно. `refresh.php`
отдаёт **данные** (JSON с массивом строк), а не HTML; проверено ответом
эндпоинта. Из этого следовало неправильное предложение «выкинуть лишний
JS-рендерер».

Что сделано по факту: третья реализация (класс `Dashboard`, 1902 строки)
оказалась **недостижимой** — `dashboard-init.js` подключается раньше и выставляет
`window.__INLINE_DASHBOARD_ACTIVE__`, по которому `dashboard.js` делает `return`
до объявления класса. Удалена.

Осталось два рендерера, и свести их в один **нельзя без потери виртуализации**:
виртуальный скроллер работает по данным (`enableFromData`), а не по готовому
HTML. Вместо объединения инвариант разметки закрыт тестом
`tests/test_renderers_in_sync.php` (20 проверок).

### 2.2. `dashboard-init.js` — *закрыто 2026-08-09*

Было 4033 строки в глобальной области: карточки статистики,
inline-редактирование, видимость колонок, копирование, тосты, автообновление,
touch-жесты. Функции объявлены глобально, поэтому любой скрипт мог их
переопределить — что и происходило (см. шапку `dashboard-stats.js` и историю с
`refreshDashboardData`).

Стало **2472 строки** — инициализация и делегированный обработчик кликов. За
семь шагов выделено шесть модулей (кастомные карточки, inline-редактирование,
константы, настройки колонок и карточек, автообновление с кнопкой «Наверх»,
touch-жесты) и удалены два мёртвых блока: недостижимый класс `Dashboard` и
отключённый через `if (false)` массовый перенос.

Попутно вскрылось главное: почти на каждом шаге находились **следы
неоконченного предыдущего рефакторинга** — четыре неподключённые сироты в
`features/` и `dashboard-init-constants.js`. Одна из них (настройки колонок)
была на 25 строк *старее* живой версии: подключи её «как готовую» — молча
откатились бы пользовательские настройки.

### 2.3. Тесты покрывают только то, что легко вызвать — *частично закрыто*

На момент разбора было восемь тестов, все — чистые функции: классификация статусов, план undo, валидация
ID, CSV, коды ответов. Не покрыто ничего, что ходит в БД: массовые операции,
частичные сбои, дедупликация, транзакции. Причина не в лени, а в дизайне:
сервисы создают соединение сами через синглтон, поэтому подменить его в тесте
нечем. Интеграционный тест в проекте один (`integration_undo_mysql.php`), и он
не в CI, потому что требует БД.

*Сделано 2026-08-08:* в гейт поднят сервис `mysql:8.0`, и `integration_*.php`
гоняются там же — в первом же прогоне 27 проверок на реальной БД. Тестов стало
десять. Не закрыто по-прежнему то, что упирается в дизайн: сервисы создают
соединение через синглтон, подменить его в юнит-тесте нечем, поэтому массовые
операции и дедуп покрыты только через интеграционный путь.

### 2.4. Наблюдаемость: логи есть, диагностики нет

`Logger` пишет уровни и контекст — это хорошо. Не хватало идентификатора запроса
и времени выполнения.

*Сделано 2026-08-08:* каждая запись начинается с `[req=<id> +<мс>]`. Теперь по
логам можно вытащить всё, что произошло в одном запросе (`grep 'req=a1b2c3d4'`),
и найти медленную страницу. Счётчика запросов к БД в логе по-прежнему нет.

## 3. Что уже хорошо и что надо просто не сломать

Честная часть: перечисленное ниже сделано на уровне, к которому не придраться.

- **Prepared statements везде**, идентификаторы (сортировка, произвольное поле)
  валидируются по фактическим метаданным таблицы, а не регуляркой.
- **Разделение сбоя и результата**: ошибка внешнего API не превращается в
  бизнес-статус (`valid`/`invalid`/`errored`) — это ровно то правило, которое
  чаще всего нарушают и потом теряют данные.
- **Undo с оптимистичной блокировкой**: строки, изменённые после действия, не
  откатываются; повторный откат блокируется атомарно.
- **Чувствительные поля не попадают в историю** (`[СКРЫТО]`) и маскируются в логах.
- **Схема чинит себя сама** и делает это аддитивно: добирает недостающие колонки,
  но никогда не меняет тип существующей и ничего не удаляет.
- **Комментарии-грабли**: там, где что-то ломалось, в коде оставлено объяснение
  «раньше было так, ломалось так, поэтому теперь так». Это редкость и это
  экономит часы.
