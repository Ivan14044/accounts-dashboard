# CLAUDE.md — правила работы с этим проектом

Файл читается ассистентом в начале каждой сессии. Он описывает **как работать**
(режим, цикл задачи, самопроверка) и фиксирует **проверенные факты** о проекте.

Порядок приоритетов при конфликте: (1) прямое указание владельца в чате →
(2) этот файл → (3) всё остальное (комментарии, README, openspec, привычки).
`AGENTS.md` — управляемый блок openspec, его правила про спеки не отменяют этот файл.

---

## ⛓️‍💥 Главное правило: проверяй РЕАЛЬНОСТЬ, а не комментарии и доки

Комментарии в коде, README, doc-файлы и openspec **могут врать или устаревать**.
Никогда не делай выводы и не давай рекомендаций на основе одного лишь текста рядом
с кодом. Проверяй, как система ведёт себя **на самом деле**.

Конкретно, прежде чем что-то утверждать или менять:

1. **Читай реальный код по цепочке**, а не его описание. Если комментарий говорит
   «лимит 100» или «иначе nginx 429» — найди, где это реально задаётся и кем
   накладывается (наш nginx? внешний API? PHP-таймаут?).
2. **Воспроизводи поведение вживую.** Внешний API — дёрни его настоящим `curl`
   (с заведомо тестовыми/фейковыми данными) и посмотри фактический формат ответа,
   коды, тайминги, реальные лимиты. Фронт/таблицу — подними локальный стенд
   (см. «Локальный стенд») и **измерь** в браузере, а не догадывайся: реальный
   замер `scrollWidth/clientWidth`, а не «по комментарию должно скроллиться».
3. **Пиши тесты / проверочные скрипты** на ключевую логику и краевые случаи.
   Особенно на то, что портит данные (классификация valid/invalid, дедуп,
   импорт/экспорт). Тест должен падать на старом баге и проходить на фиксе.
4. **Числа из чужих слов и из комментариев — гипотеза, а не факт.** Подтверждай
   измерением. Пример: заявленный «лимит 3000 за запрос» у check.fb.tools при
   проверке оказался не потолком — API принимает и 5000 (HTTP 200, ~8с); реальное
   ограничение — время/размер ответа, а не число 3000.
5. **Если проверить невозможно** (нет доступа, нет окружения) — скажи об этом явно
   и не выдавай предположение за установленный факт.

Цель: выводы и правки опираются на наблюдаемое поведение, а не на то, что
кто-то когда-то написал в комментарии.

## Режим работы: автономный, качество важнее скорости

Владелец не хочет пошагового согласования. Работай самостоятельно и доводи задачу
до конца — включая тесты, живую проверку и документацию. Объём работы не повод
сокращать: если надо перелопатить 30 файлов и поднять стенд — делай.

### Решай сам (не спрашивай)
- Имена переменных/функций/файлов, структура модуля, порядок аргументов.
- Локальные рефакторинги внутри задачи, вынос дублей, разбиение длинной функции.
- Выбор способа проверки: тест / curl / стенд / замер в браузере.
- Мелкие UI-детали в рамках существующего дизайна: отступы, состояния
  hover/focus/disabled, тексты подсказок, порядок пунктов меню.
- Исправление явного бага, найденного по пути, если фикс маленький и покрыт тестом
  (обязательно расскажи об этом в отчёте отдельным пунктом).
- Добавление комментария/докблока, обновление документации.

Правило принятия решения: сформулируй 2–3 варианта, оцени их по критериям
«корректность данных → простота → согласованность с текущим кодом →
производительность», выбери и **зафиксируй причину выбора** в комментарии или в
отчёте. Не устраивай опрос владельца по вопросам, которые решаются этим анализом.

### Спрашивай обязательно (стоп-лист)
- Мёрдж в `main` — это **немедленный деплой в прод**. Только с явного согласия.
- Любая правка/удаление данных в боевой БД, ручные миграции на проде.
- Смена контракта API, формата экспорта/импорта, схемы БД, семантики статусов.
- Удаление фич, файлов или таблиц; массовые переименования публичных функций.
- Новые внешние зависимости и новые обращения к сторонним сервисам.
- Всё, что меняет поведение денег/доступов/безопасности.

### Улучшения «от себя»
Бойскаутское правило в границах: улучшай то, чего касаешься. Заметил проблему
вне задачи — не расширяй молча PR: либо мелкий безопасный фикс с тестом и
пометкой в отчёте, либо запись в отчёт «нашёл, не трогал, вот почему».
Не превращай задачу в бесконечный рефакторинг всего проекта.

## Обязательный цикл задачи

1. **Разведка.** Прочитай реальный код по цепочке фронт → API → сервис → БД.
   Найди, где логика уже реализована, чтобы не плодить дубль (в проекте это
   реальная боль: см. предупреждение в шапке `dashboard-stats.js`).
2. **План.** Сформулируй, что меняется, какие краевые случаи, что может сломаться,
   как это будет проверено. Для крупных изменений — сначала openspec-предложение
   (см. `openspec/AGENTS.md`).
3. **Тест вперёд.** Сначала тест, который **падает** на текущем поведении.
   Убедись глазами, что он красный и падает по правильной причине.
4. **Реализация** минимальным понятным кодом в конвенциях проекта.
5. **Тест зелёный** — прогони весь набор, а не один файл, и на обеих версиях PHP.
6. **Самопроверка** по чеклисту ниже (обязательно, каждый раз).
7. **Живая проверка** на локальном стенде: страница рендерится, консоль чистая,
   `php_errors.log` без новых Warning/Fatal, UI-сценарий отрабатывает.
8. **Документация и комментарии** обновлены (см. раздел про доки).
9. **Отчёт владельцу:** что сделано, чем это подтверждено (команды и результат),
   какие решения приняты самостоятельно и почему, что осталось за скобками.

## Самопроверка: после каждой функции и каждого модуля

Не «написал всё → проверил в конце». Проверяй по мере: закончил осмысленный
кусок — сразу прогони его.

**После каждой функции:**
- Что она возвращает на пустом входе, `null`, `0`, `''`, на огромном входе?
- Все ветки кода реально достижимы? Есть ли ранний выход, который всё глотает?
- Ошибка внешнего мира (БД, сеть, API) отличима от «данные плохие»? Сбой **никогда**
  не должен молча превращаться в бизнес-результат (см. правило valid/invalid/errored).
- Побочные эффекты названы в имени функции? Функция `getX()` не должна писать в БД.
- Есть докблок: назначение, параметры, возврат, неочевидные краевые случаи.

**После каждого модуля / перед тем, как считать задачу сделанной:**
- `php -l` по изменённым файлам + весь набор тестов на PHP 7.4 **и** 8.2.
- Перечитай собственный diff целиком, как чужой код: нет ли отладочного мусора,
  закомментированного кода, `console.log`, TODO без объяснения, лишних файлов.
- Не сломаны ли соседние сценарии: экспорт, импорт, корзина, undo, фильтры,
  избранное — если менял общие места (`AccountsService`, `FilterBuilder`,
  партиалы таблицы, `Database`).
- Совпадает ли поведение с тем, что написано в комментариях и доках рядом.
  Если нет — правится **и то, и другое**.
- Живая проверка выполнена и её результат ты видел своими глазами.

Формулируй результат честно: «проверено так-то, вот вывод команды». Если что-то
не проверено — так и пиши, а не «должно работать».

## Тесты

Тесты лежат в `tests/`, фикстуры — в `tests/fixtures/`. Локального PHP на машине
нет, всё гоняется в Docker.

```bash
docker run --rm -v "$PWD":/app -w /app php:7.4-cli bash -c 'for t in tests/test_*.php; do echo "── $t"; php "$t" || exit 1; done'
```

Правила:
- **Имя `tests/test_*.php`** — такой файл автоматически попадает в CI-гейт
  (`lint.yml` гоняет их глобом). Тест обязан быть самодостаточным: без сети,
  без БД, без секретов; код выхода 0 = успех, 1 = падение.
- Тесты, требующие БД, называются иначе (`tests/integration_*.php`) и **сами
  скипаются** (exit 0), если нет `TEST_DB_*` — рецепт запуска описан в шапке
  `tests/integration_undo_mysql.php`.
- Проверяй на **обеих** версиях PHP: `php:7.4-cli` (как в CI) и `php:8.2-cli`.
  Разница реальна: `count()` без аргумента на 7.4 — Warning, на 8.x — фатальная
  `ArgumentCountError`. Версия PHP на проде нам не видна (`X-Powered-By` скрыт),
  поэтому код должен быть корректен на обеих.
- Тест на баг пишется **до** фикса и должен падать. Красный тест, который ты не
  видел красным, ничего не доказывает.
- Приоритет покрытия: всё, что может **испортить данные** — классификация статусов,
  undo, дедуп, импорт/экспорт CSV, валидация ID, миграции; и вся чистая логика,
  которую можно вызвать без БД.
- В тесте включай строгий режим: `set_error_handler`, превращающий Warning/Notice
  в исключение (пример — `tests/test_empty_state_colspan.php`). На проде
  `error_reporting=E_ALL`, и Warning в шаблоне реально обрывает рендер.

## Локальный стенд

*(Рецепт поднят и проверен целиком 2026-08-08 в этом воркспейсе.)*

Полноценный дашборд поднимается локально за пару минут — используй его для живой
проверки вместо гаданий и вместо экспериментов на проде.

```bash
docker network create dash-local
docker run -d --name dash-mysql --network dash-local -e MYSQL_ALLOW_EMPTY_PASSWORD=yes -e MYSQL_DATABASE=dashboard mysql:8.0
docker run -d --name dash-php --network dash-local -p 8099:8080 -v "$PWD":/app -w /app php:7.4-cli sh -c 'docker-php-ext-install mysqli >/dev/null 2>&1; PHP_CLI_SERVER_WORKERS=4 php -S 0.0.0.0:8080'
```

Важные детали, подтверждённые на практике:
- **Схему создавать руками не нужно.** `sql/create_all_tables.sql` падает на пустой
  базе (`account_history` ссылается на ещё не существующую `accounts`). Таблицу
  `accounts` и индексы создаёт само приложение при первом заходе —
  `includes/DatabaseSchemaManager.php::validateAndMigrate()`.
- Вход — только строка подключения (пароль пользователя не нужен, БД без пароля):
  `server=dash-mysql;port=3306;user id=root;password=;database=dashboard`.
- Логин скриптом (без формы) — забрать CSRF и отправить POST:

```bash
TOKEN=$(curl -s -c cj.txt http://localhost:8099/login.php | grep -o 'name="csrf_token" value="[^"]*"' | sed 's/.*value="//;s/"//'); curl -s -b cj.txt -c cj.txt -o /dev/null -w "%{http_code} %{redirect_url}\n" -d "csrf_token=$TOKEN" -d "db_connection_string=server=dash-mysql;port=3306;user id=root;password=;database=dashboard" http://localhost:8099/login.php
```

- Тестовые строки наливай сам (`INSERT INTO accounts ...`) — только заведомо
  фейковые данные, никаких боевых дампов на локалку.
- Ошибки PHP пишутся в `php_errors.log` в корне (в `.gitignore`). Перед проверкой
  чисти его (`: > php_errors.log`) и после сценария смотри, что он пуст.
- Убрать за собой: `docker rm -f dash-php dash-mysql && docker network rm dash-local`.

## Живая проверка в браузере

Правило: **UI считается работающим только после того, как ты открыл его в браузере
и измерил.** Скриншот показывает, что нарисовалось; JS-замеры показывают правду о
вёрстке; консоль показывает, что сломалось молча.

Чем пользоваться:
- **Локальный стенд + встроенный браузер** (`mcp__Claude_Browser__*`) — основной
  способ. Своя сессия, можно жать любые кнопки, ничего не испортишь.
- **Chrome владельца** (`mcp__claude-in-chrome__*`) — только когда нужна его живая
  сессия на проде. Там: **read-only**. Смотреть, читать консоль/сеть, мерить.
  Ничего не удалять, не сохранять, не запускать массовые операции, не вводить
  пароли и токены. Любое действие, меняющее данные на проде, — сначала спросить.

Проверенный порядок работы со встроенным браузером:
1. `preview_start` с `url: http://localhost:8099/login.php`.
2. Размер вьюпорта задавать **числами**: `resize_window {width: 1280, height: 800}`.
   Пресет `desktop` в этой сессии дал вьюпорт `0x0` — замеры были бы мусором.
   После установки размера всегда сверяйся: `innerWidth/innerHeight` не нулевые.
3. Логин: заполнить `textarea[name=db_connection_string]` и отправить форму.
4. Проверка страницы: `read_console_messages {onlyErrors:true}` должен быть пуст,
   `computer{action:'screenshot'}` — для глаз, `javascript_tool` — для чисел.

Минимальный набор замеров вёрстки (гонять на 1280×800 и на 375×812):

```js
const w = document.querySelector('#tableWrap');
JSON.stringify({
  bodyOverflow: document.body.scrollWidth - document.documentElement.clientWidth, // ДОЛЖЕН быть 0
  tableScrollable: w ? w.scrollWidth > w.clientWidth : null,   // таблица скроллится внутри себя
  rows: document.querySelectorAll('#accountsTable tbody tr').length
});
```

Критерии приёмки UI:
- Горизонтального скролла у `body` нет ни на одной ширине; широкая таблица
  скроллится **внутри** своего контейнера.
- Ничего не наезжает и не обрезается на 375px, 768px, 1280px, 1920px.
- Консоль без ошибок и без необработанных промисов; сеть без 4xx/5xx на обычном
  сценарии; `php_errors.log` без новых записей.
- Есть состояния: загрузка, пусто, ошибка. Пустая выдача — это отдельный
  проверяемый кейс, а не «ну там ничего нет».
- Тёмная тема не сломана (в проекте есть переключатель и `[data-bs-theme="dark"]`).
- Клавиатура: фокус видим, по Tab можно дойти до основных действий, у иконочных
  кнопок есть `aria-label`/`title`.
- Анимации не мешают: без дёрганий при обновлении таблицы и открытии панелей.

## Как писать и подключать модули (конвенции проекта)

Общее: **сначала ищи, где это уже есть**. Дубль логики в этом проекте уже приводил
к молчаливым багам (перезапись глобальных функций в `dashboard-stats.js`).

**PHP-бэкенд**
- Доступ к БД — только `Database::getInstance()`; `global $mysqli` в новом коде нет.
- Запросы — исключительно prepared statements; никакой конкатенации пользовательского
  ввода в SQL. Имена таблиц/колонок — через `TableResolver`/`ColumnMetadata`,
  не из запроса напрямую.
- Логика живёт в сервисе (`includes/*Service.php`), доступ к данным — в репозитории,
  сборка условий — в `FilterBuilder`. Точка входа (`*.php` в корне, `api/routes/*`)
  только валидирует вход и вызывает сервис.
- Логирование — `Logger`, а не `echo`/`var_dump`. Не логируй секреты, хост/логин БД,
  cookies, токены.

**API**
- Новый эндпоинт = маршрут в `api/routes/<resource>.php`; файл подключается в
  `api/index.php` и получает `$router` и `$tableName` из его scope. Auth и
  rate-limit уже навешаны глобальным middleware — не дублируй.
- Ответ — единый JSON-контракт (`success` + данные / `error`), коды HTTP по смыслу.
  401 для неавторизованных AJAX, а не редирект.

**JavaScript**
- Модуль — отдельный файл в `assets/js/modules/`, наружу торчит один объект
  `window.DashboardXxx = { init, ... }`, остальное внутри. Инициализация — из
  `dashboard-main.js`, а не в момент загрузки файла.
- Порядок подключения скриптов задан в шаблонах — новый модуль ставь в правильное
  место и проверь, что зависимости уже загружены.
- Логирование — `logger.debug/warn/error`, не `console.log`.
- DOM — через `domCache`, частые обработчики — через `debounce`/`batchDOM` из
  `performance.js`. Никаких дорогих операций в обработчике скролла.
- Ассеты подключаются с `?v=<?= ASSETS_VERSION ?>` — константа авто-бампится при
  деплое, руками её не трогай.

**Шаблоны**
- Разметка — в `templates/partials/...`, партиал самодостаточен: не полагайся на
  переменную, которая «должна быть» в scope. Нормализуй вход в начале файла
  (`$X = isset($X) && is_array($X) ? $X : [];`) — иначе Warning/фатал в проде.
- Любой вывод пользовательских данных экранируется (`e()` / `htmlspecialchars`).
- Изменил число колонок таблицы — проверь `colgroup`, `thead`, `rows.php`,
  `empty-state.php` и JS-рендер (`table-module.js`, `dashboard-refresh.js`):
  colspan/порядок колонок живут в пяти местах и легко расходятся.

## Комментарии и документация

Цель: новый программист открывает проект и понимает его без расспросов.

- Комментарий объясняет **почему**, а не пересказывает код. Лучший комментарий в
  этом репозитории — тот, что описывает грабли: «раньше было так, ломалось вот
  так, поэтому теперь так» (см. шапки `lint.yml`, `dashboard-stats.js`).
- У каждой публичной функции/класса — докблок: назначение, `@param`, `@return`,
  краевые случаи и опасности. У каждого файла-модуля — шапка: за что отвечает и
  чего в нём осознанно **нет**.
- Язык комментариев — русский, как и весь проект.
- Никаких «мёртвых» комментариев: закомментированный код удаляется, устаревший
  комментарий правится вместе с кодом. Комментарий, противоречащий коду, — баг.
- TODO обязан содержать причину и условие снятия, иначе он не нужен.
- Что обновлять при изменениях: `CHANGELOG.md` (что поменялось для пользователя),
  `DEVELOPER_GUIDE.md` (структура, модули, как добавить фичу), `USER_GUIDE.md`
  (если поменялся UI-сценарий), и раздел «Проверенные факты» ниже — если ты
  выяснил что-то новое про реальное поведение системы.

## Безопасность и данные

- Не портить данные важнее, чем показать результат. Сбой внешнего API/БД/таймаут —
  это «не проверено» (`errored`), а не бизнес-статус.
- Секреты (FTP, токены, пароли БД) — только в GitHub Secrets и в сессии. В коде,
  логах, коммитах и отчётах их быть не должно. `.claude/`, `*.log`, `users.json`,
  `.env` — в `.gitignore`, туда же уходят все временные артефакты.
- На проде и в чужом браузере — режим наблюдателя. Массовые операции, удаления и
  миграции на боевой БД — только по явному согласию владельца.
- Внутренние файлы (`tests/`, внутренние доки) не должны уезжать на публичный
  домен — см. список `exclude` в `deploy.yml`.

### Деплой и CI
- Автодеплой — workflow **Deploy to FTP** ([.github/workflows/deploy.yml](.github/workflows/deploy.yml)),
  триггер: **push в `main`** (и ручной). PR-уровневого деплоя нет. *(проверено по
  факту: мёрдж в main → запуск Deploy to FTP → success.)*
- Ветка `main` защищена и требует обязательный статус-чек **`lint`**
  ([.github/workflows/lint.yml](.github/workflows/lint.yml)). Без зелёного `lint`
  PR не сольётся. *(проверено: PR висел BLOCKED, пока чек не появился/прошёл.)*
  Отсюда важное следствие: **имя job обязано остаться `lint`**. Не превращай его в
  matrix — имена станут `lint (7.4)`/`lint (8.2)`, required-чек перестанет
  находиться и все PR встанут. Вторая версия PHP гоняется вторым `setup-php`
  внутри того же job.
- Гейт `lint` = `php -l` по всем PHP-файлам (PHP 7.4) + все `tests/test_*.php`
  на PHP 7.4 и 8.2. *(проверено локально в Docker 2026-08-08: `php -l` по всему
  репозиторию чист и на 7.4, и на 8.2; все пять тестов зелёные на обеих версиях.)*
- `ASSETS_VERSION` авто-бампится в деплое на короткий SHA коммита (cache-buster
  для CSS/JS). Прод грузит исходные `assets/css/core-*.css` напрямую, **не**
  минифицированный бандл (`build_assets.php` — отдельный, страницами не
  используется). *(проверено grep по `*.php`.)*
- Версия PHP на проде неизвестна: `X-Powered-By` скрыт. *(проверено `curl -I`
  по `panel.account-factory.site/login.php` 2026-08-08 — есть только Cloudflare
  и security-заголовки.)* Поэтому совместимость держим и с 7.4, и с 8.x.

### Проверка аккаунтов на валидность (check.fb.tools)
Поток: фронт [dashboard-validate.js](assets/js/modules/dashboard-validate.js) режет
выбор на партии и шлёт на наш `POST /api/accounts/validate/check`
([api/routes/accounts.php](api/routes/accounts.php)) → сервер
[AccountValidationService.php](includes/AccountValidationService.php) дробит на
суб-батчи и параллельно (`curl_multi`) обращается к check.fb.tools → ответ
маппится в valid / invalid / **errored (не проверено)**.

Реальный контракт API *(проверено живыми curl-запросами)*:
- `POST https://check.fb.tools/api/check/account`, тело
  `{"inputData":[...],"checkFriends":false,"userLang":"ru"}`.
- Ответ: `data[].account`, `data[].uid`, `data[].status.name` (`valid`|`invalid`),
  плюс `data[].status.message` и сводка `info:{valid,invalid,errors,noExist}`.
- Размер партии: API принимает **минимум 5000 ID за запрос** (HTTP 200). Тайминги:
  3000 → ~4.7с, 5000 → ~8с. «3000» — не жёсткий лимит. Текущий
  `FB_TOOLS_BATCH_SIZE=100` сильно занижен ⇒ лишние десятки запросов ⇒ риск
  rate-limit. Кандидат на увеличение (с запасом по `FB_TOOLS_TIMEOUT`).
- Комментарий `CONCURRENCY=1 — иначе nginx 429` относится к **нашему** серверу,
  а не к check.fb.tools.

КРИТИЧНО по корректности: сбой/таймаут/частичный ответ внешнего API **нельзя**
трактовать как `invalid` — иначе валидные аккаунты портятся статусом. Такие
случаи идут в `errored` («не проверено»). См. фикс в `checkItems` /
`checkFbIdsBulk` / `parseHandleResult`.
