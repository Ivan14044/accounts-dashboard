# CLAUDE.md — правила работы с этим проектом

## ⛓️‍💥 Главное правило: проверяй РЕАЛЬНОСТЬ, а не комментарии и доки

Комментарии в коде, README, doc-файлы и openspec **могут врать или устаревать**.
Никогда не делай выводы и не давай рекомендаций на основе одного лишь текста рядом
с кодом. Проверяй, как система ведёт себя **на самом деле**.

Конкретно, прежде чем что-то утверждать или менять:

1. **Читай реальный код по цепочке**, а не его описание. Если комментарий говорит
   «лимит 100» или «иначе nginx 429» — найди, где это реально задаётся и кем
   накладывается (наш nginx? внешний API? PHP-таймаут?).
2. **Воспроизводи поведение вживую.** Внешний API — дёрни его настоящим `curl`
   (с заведомо тестовыми/фейковыми данными) и посмотри фактический формат ответа,
   коды, тайминги, реальные лимиты. Фронт/таблицу — отрендерь в headless Chrome и
   измерь, а не догадывайся (см. как проверяли мобильный скролл: реальный замер
   `scrollWidth/clientWidth`, а не «по комментарию должно скроллиться»).
3. **Пиши тесты / проверочные скрипты** на ключевую логику и краевые случаи.
   Особенно на то, что портит данные (классификация valid/invalid, дедуп,
   импорт/экспорт). Тест должен падать на старом баге и проходить на фиксе.
4. **Числа из чужих слов и из комментариев — гипотеза, а не факт.** Подтверждай
   измерением. Пример: заявленный «лимит 3000 за запрос» у check.fb.tools при
   проверке оказался не потолком — API принимает и 5000 (HTTP 200, ~8с); реальное
   ограничение — время/размер ответа, а не число 3000.
5. **Если проверить невозможно** (нет доступа, нет окружения) — скажи об этом явно
   и не выдавай предположение за установленный факт.

Цель: выводы и правки опираются на наблюдаемое поведение, а не на то, что
кто-то когда-то написал в комментарии.

## Проверенные факты о проекте (подтверждены, а не «из доки»)

> Здесь — только то, что реально проверено. Дату/способ проверки указывай.

### Деплой и CI
- Автодеплой — workflow **Deploy to FTP** ([.github/workflows/deploy.yml](.github/workflows/deploy.yml)),
  триггер: **push в `main`** (и ручной). PR-уровневого деплоя нет. *(проверено по
  факту: мёрдж в main → запуск Deploy to FTP → success.)*
- Ветка `main` защищена и требует обязательный статус-чек **`lint`**
  ([.github/workflows/lint.yml](.github/workflows/lint.yml) — `php -l` по всем
  PHP-файлам на PR). Без зелёного `lint` PR не сольётся. *(проверено: PR висел
  BLOCKED, пока чек не появился/прошёл.)*
- `ASSETS_VERSION` авто-бампится в деплое на короткий SHA коммита (cache-buster
  для CSS/JS). Прод грузит исходные `assets/css/core-*.css` напрямую, **не**
  минифицированный бандл (`build_assets.php` — отдельный, страницами не
  используется). *(проверено grep по `*.php`.)*

### Проверка аккаунтов на валидность (check.fb.tools)
Поток: фронт [dashboard-validate.js](assets/js/modules/dashboard-validate.js) режет
выбор на партии и шлёт на наш `POST /api/accounts/validate/check`
([api/routes/accounts.php](api/routes/accounts.php)) → сервер
[AccountValidationService.php](includes/AccountValidationService.php) дробит на
суб-батчи и параллельно (`curl_multi`) обращается к check.fb.tools → ответ
маппится в valid / invalid / **errored (не проверено)**.

Реальный контракт API *(проверено живыми curl-запросами)*:
- `POST https://check.fb.tools/api/check/account`, тело
  `{"inputData":[...],"checkFriends":false,"userLang":"ru"}`.
- Ответ: `data[].account`, `data[].uid`, `data[].status.name` (`valid`|`invalid`),
  плюс `data[].status.message` и сводка `info:{valid,invalid,errors,noExist}`.
- Размер партии: API принимает **минимум 5000 ID за запрос** (HTTP 200). Тайминги:
  3000 → ~4.7с, 5000 → ~8с. «3000» — не жёсткий лимит. Текущий
  `FB_TOOLS_BATCH_SIZE=100` сильно занижен ⇒ лишние десятки запросов ⇒ риск
  rate-limit. Кандидат на увеличение (с запасом по `FB_TOOLS_TIMEOUT`).
- Комментарий `CONCURRENCY=1 — иначе nginx 429` относится к **нашему** серверу,
  а не к check.fb.tools.

КРИТИЧНО по корректности: сбой/таймаут/частичный ответ внешнего API **нельзя**
трактовать как `invalid` — иначе валидные аккаунты портятся статусом. Такие
случаи идут в `errored` («не проверено»). См. фикс в `checkItems` /
`checkFbIdsBulk` / `parseHandleResult`.
